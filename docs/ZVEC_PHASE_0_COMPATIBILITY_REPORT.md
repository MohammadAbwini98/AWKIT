## 0B.2 Correction to the Phase 0 "environmentally blocked" diagnosis

Phase 0 §17.1 recorded that `app.whenReady()` never resolved and attributed it to a missing interactive
Window Station. **That diagnosis was wrong in its cause, though right that it was not a Zvec defect.** Phase
0B established:

- The session **is** interactive (evidence above).
- Launching the **packaged** `SpecterStudio.exe` (double-click via File Explorer, and via a `.bat`
  launcher) reaches `app.whenReady()` **reliably every time**.
- Launching **`electron.exe <script.mjs>`** — a bare Electron invocation with a script argument — still
  never reaches `app.whenReady()`, whether spawned from Git Bash, from PowerShell `Start-Process`, from a
  GUI-double-clicked `.bat`, or via Playwright's `_electron.launch()`.

So the blocker is specific to the *bare `electron.exe` + script-path* invocation form in this environment,
not to Electron app mode. Phase 0B therefore ran all app-mode tests through a temporary,
env-var-gated hook inside the **real** packaged AWKIT main process (`AWKIT_ZVEC_SPIKE_HOST`), which is a
strictly better test than the standalone entry points would have been.

## 0B.4 Two important findings

### Finding A — bundling the Zvec caller into the electron-vite main chunk causes a hard native crash

First app-mode attempt loaded the spike code as a **Vite-bundled chunk** (the same way AWKIT's production
main process is built). Result, captured in a disk-flushed step trace:

```
runMain:zvec-loaded exports=17        ← native module loads fine
step:begin jiebaDictDirAutoResolved
step:ok   jiebaDictDirAutoResolved    ← dictionary resolution fine
step:begin createCollection
<process gone — no JS error, no uncaughtException, no dialog>
```

Re-running the **identical operations from raw, unbundled `.mjs` files on disk** (shipped via
`asarUnpack`, imported by absolute `file://` URL) in the **same** packaged app-mode main process: **all 13
steps pass.** The only variable changed was bundled-vs-unbundled.

This is a **serious Phase 1 finding**, because AWKIT's production main process *is* bundled by
electron-vite. Phase 1 must externalize the Zvec adapter from the main-process bundle (as
`playwright`/`sql.js` already are) and must add a regression check that proves it stays externalized. Root
cause was not investigated further in Phase 0B (out of scope); the actionable requirement stands regardless.

### Finding B — main-process placement has a whole-app blast radius; utility placement does not

Both were observed directly in this session, not inferred:

- Main-process crash (Finding A): **entire application terminated**.

buffered its samples and emitted only on completion, so `Stop-Job` discarded all of them. The harness was
rewritten to wait for the utility host to appear before starting the workflow, sample in the foreground

## 0D.9 Final placement recommendation

**UTILITY PROCESS - confirmed, now on repeated measurement against the production-shaped host.**

1. Crash containment directly observed: native abort -> exit 134 detected in 84.62 ms, main process
   survived, window responsive, authoritative stores readable, pending request failed with a stable
   `SEMANTIC_HOST_EXITED`. Phase 0B showed the equivalent crash in main-process placement destroys the
   whole application.
2. Memory isolation: main-process growth **+1.77 MB** while the host held 204.8-330 MB.
3. No performance penalty: FTS p50 4.42 ms, vector p50 1.67 ms, 11,921 docs/sec insertion.
4. Coexistence: real Playwright workflow 84/0 in every scenario, including a mid-workflow host crash.

## 0D.10 Shutdown recommendation

**Utility-process graceful close followed by bounded termination** (unchanged from 0B, now with
percentiles): graceful shutdown p50 **0.592 ms** / p99 **0.631 ms** (n=16); collection close p50
**11.141 ms** / p99 **12.360 ms** (n=15).

Both are far inside the existing 2,000 ms `before-quit` envelope, so the ~690 ms in-main close measured in
0B is no longer the concern it was. Phase 1A should still give the semantic host its **own** bounded
stage - a 2,000 ms graceful window then forced kill - rather than adding a fourth entry to the shared
`Promise.race`, because these figures are for a 1,200-document corpus with no production write queue, and
the orphaned-generation finding (0D.7) shows unclean termination is a real path needing reconciliation.
