# N2.4 — Single-capture candidate fan-out (`awkit-vra.12.4`)

Status: implemented and measured on 2026-10-12, baseline `76978ba6`. N2 is still **shadow-only**.
`MEASURED_FUSION_POLICY.contradictionEnabled` is still `false`. N2.6 (enforce-veto) is still deferred.

## Why

N2.3 measured four separate element captures for each fusion evaluation: one for the winner and three for the
competitors. That took a median of 499 ms and a p95 of 1111 ms, which is over the FD-5 budget of 400 ms. The owner
re-scoped N2.4 to fix this: take **one** immutable viewport screenshot per visual decision cycle, and cut every
candidate's crops, fingerprint and evidence from it. The former N2.4 scope, the `VisualReferenceStore` sidecar and
the passing-resolve refresh, moves to its own bead. That bead must block N2.5 (see *Tracker* below).

## Architecture (`src/visual/internal/captureCore.ts`, public surface in `src/visual/capture.ts`)

- **`VisualCaptureFrame`** — one immutable viewport screenshot. Its public fields are metadata only: `captureId`
  (a random UUID), the frozen `viewport`, `capturedAt`, `durationMs` and `memory`. The decoded pixels and the page
  are held in an ECMAScript private field, so serialising a frame never carries an image or a Playwright object.
  Only a capture can construct a frame; the constructor is guarded by a module-private key.
- **`captureVisualFrame(page, options)`** — the guard runs before and after the screenshot. The screenshot is
  decoded once and the encoded PNG is dropped.
- **`cropFromVisualFrame(frame, cssRect, padding)`** — a deterministic crop with the same outward rounding and clamp
  as the N0 element path. A crop is pixel-identical to the element's solo `captureElement` crop.
- **`validateVisualFrame(page, frame)`** — re-measures the viewport. A size, DPR or pinch change gives
  `CAPTURE_STALE`.
- **`releaseVisualFrame(frame)`** — idempotent. It unbinds the pixels and the page watch. Every later crop is
  `CAPTURE_STALE`.
- **`captureCandidates(page, [{id, target}], options)`** runs the whole cycle and returns `VisualCandidateFanout`:
  1. Resolve and measure every candidate (count = 1, owner frame on this page, inside the viewport).
  2. Take one screenshot, unless no candidate resolved; then it takes zero.
  3. Run the post-capture guard and prove the frame still describes the page.
  4. Re-measure each candidate. A candidate that moved is `TARGET_STALE`, scoped to that candidate.
  5. Crop each candidate from the same frame.
  6. Release the frame in `finally`.

  It returns per-phase timing (resolve, screenshot, decode, recheck, crop, total) and memory (PNG, decoded, crops,
  peak temporary bytes). The list is capped at `VISUAL_FANOUT_MAX_CANDIDATES = 32`, with unique non-empty ids.
- **`buildCandidateEvidence(fanout)`** (`src/visual/candidateEvidence.ts`) — each candidate gets its N1 fingerprint,
  its `captureId`, a failure if it has one, and size counts. It never carries screenshot bytes, crop bytes, the frame
  or a page.

## Failure scope

- **Candidate-scoped:** `TARGET_STALE`, `TARGET_NOT_UNIQUE`, `TARGET_OFFSCREEN`, `FRAME_MAPPING_FAILED`, a crop
  clipped away. Other candidates are unaffected, and **nothing is recaptured** for the failed one.
- **Cycle-fatal (`CYCLE_FATAL`):** `PROTECTED_SURFACE`, `CAPTURE_STALE`, `PAGE_CLOSED`, `BUDGET_EXHAUSTED`,
  `CANCELLED`. The cycle aborts and returns no crops.

## Invalidation (`CAPTURE_STALE`)

| Reason | Detected by |
|---|---|
| `navigated` | main-frame `framenavigated` after the screenshot |
| `popup` | a `popup` event after the screenshot |
| `page-closed` | `close`, or a guard failure on a closed page |
| `viewport-changed` | the post-capture re-measure: CSS size, DPR or `visualViewport.scale` changed |
| `expired` | older than `maxFrameAgeMs` (default 5000) |
| `released` | any crop after `releaseVisualFrame` |

A navigation that lands while the candidates are being cropped is caught by a final stale check, and the whole
cycle is refused. Fusion treats `CAPTURE_STALE` as R2 (`dom-only/capture-failed`); `verify:visual-fusion` has the
row.

## Frames

Playwright's `boundingBox()` already reports iframe and nested-iframe elements in main-viewport CSS pixels. So
top-level, iframe and nested-iframe candidates share the one screenshot, and the crop records `isMainFrame` and
`depth`. A frame belonging to a different page or a detached frame gives `FRAME_MAPPING_FAILED` for that candidate.

## Security

The protected-surface scan runs **exactly once before** the screenshot and **exactly once after** it, whatever the
candidate count. Before N2.4 it ran twice for each element capture. A protected surface found by either scan aborts
the cycle with `PROTECTED_SURFACE`, and no crop is returned. Protected-login handoff rules are unchanged.

## Concurrency and memory

- **Concurrency:** each cycle owns its frame. No frame or capture is stored globally and there is no cache.
  Concurrent cycles on two pages produce two independent `captureId`s and screenshots.
- **Memory:** the frame's decoded pixels are reachable only until `releaseVisualFrame`, which runs in `finally`.
  Page listeners (`framenavigated`, `popup`, `close`) are detached at release, and the verifier asserts the
  listener counts return to their baseline.
- **Measured peak transient image bytes:** median 3.06 MB, max 7.83 MB at DPR 2, for winner + 3 candidates.
- **Nothing is written to disk.** There is no image cache directory, hidden capture storage, persistent candidate
  crop, or workflow screenshot.

## Performance — `npm run benchmark:visual-fusion` (informational)

The benchmark ran 432 evaluations (winner + 3 competitors), headless and headed, at DPR 1, 1.25 and 2. The two
paths alternated which ran first. Real screenshots were counted with a `page.screenshot` wrapper.

| Path | Screenshots per evaluation | Median | p95 | Max |
|---|---|---|---|---|
| N2.3 recorded baseline | 4 | 499 ms | 1111 ms | — |
| Same-run sequential (4× `captureElement`) | 4 | 467 ms | 723 ms | — |
| **N2.4 fan-out** (capture + evidence + shadow fusion) | **1** | **171 ms** | **237 ms** | 288 ms |

The fan-out median is 63% faster than the sequential path in the same run.

| Group | Fan-out median / p95 | Sequential median |
|---|---|---|
| headless DPR 1 | 130 / 147 | 312 |
| headless DPR 1.25 | 159 / 185 | 427 |
| headless DPR 2 | 222 / 245 | 692 |
| headed DPR 1 | 156 / 172 | 420 |
| headed DPR 1.25 | 174 / 202 | 482 |
| headed DPR 2 | 222 / 260 | 668 |

Where the fan-out time goes, by phase median:

| Phase | Median | Share |
|---|---|---|
| resolve | 55 ms | 32% |
| screenshot | 46 ms | 27% |
| decode | 28 ms | 17% |
| guards + other | 26 ms | 15% |
| recheck | 8 ms | 5% |
| fingerprints | ~1 ms | — |
| fusion | ~0 ms | — |
| crops | ~0 ms | — |

Other results:

- Fingerprints were identical to the sequential captures in 432/432 evaluations.
- 66/66 structural rows PASS.
- Separation is unchanged (not separated), and there were 0 false vetoes.
- The headed Ctrl+zoom capture is still refused with `CAPTURE_UNAVAILABLE`.

### FD-5 decision: **PASS**

The p95 is 237 ms against the **unchanged** 400 ms budget, and it is under budget in every group; the worst group,
headed DPR 2, has a p95 of 260 ms. The benchmark applies the classifier mechanically, in this order:

1. **INCONCLUSIVE** — too few samples, or any cycle that did not take exactly 1 screenshot.
2. **REGRESSION** — the median is ≥10% slower than sequential.
3. **PASS** — p95 ≤ 400 ms.
4. **IMPROVED BUT ABOVE BUDGET** — the median is ≥10% faster.
5. **NO MATERIAL IMPROVEMENT** — otherwise.

The budget was not altered.

### Remaining bottleneck for N2.5

**Resolve** is the largest phase: per-candidate `count()`, `elementHandle()`, owner frame and bounds, about 14 ms
per candidate. Next come screenshot and decode. N2.5 wires the shadow stage into `LocatorFactory.recover()`. There
the DOM recovery has already resolved its candidates, so the adapter should reuse those handles and bounds rather
than resolve them again. That is the measured lever.
